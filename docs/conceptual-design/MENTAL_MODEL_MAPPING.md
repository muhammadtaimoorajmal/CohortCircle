# Mental Model Mapping & Cognitive Alignment: CohortCircle

> **Governance Category:** Cognitive Ergonomics & Mental Model Translation  
> **Status:** **EIGHT CORE DOMAIN MAPPINGS SPECIFIED**  
> **Integrity Notice:** Mappings bridge common student assumptions with clear, non-confusing UI metaphors, eliminating cognitive friction and terminology ambiguity.

---

## 1. Cognitive Architecture & Translation Principle

Students arrive with ingrained mental models shaped by legacy communication tools (WhatsApp, Discord, campus bulletin boards, Doodle polls). Often, these legacy mental models cause confusion when applied to structured peer learning (e.g., assuming a "study group" is an open broadcast chat with no capacity limits).

CohortCircle translates these expectations into predictable, supportive interface patterns:

```
┌───────────────────────────┐         ┌───────────────────────────┐         ┌───────────────────────────┐
│  Student Legacy Model     │ ──────> │   Cognitive Translation   │ ──────> │  CohortCircle UI Concept  │
│ (Chat Rooms / Ad-hoc DMs) │         │  (Addressing Ambiguities) │         │ (Chartered Circles/RSVPs) │
└───────────────────────────┘         └───────────────────────────┘         └───────────────────────────┘
```

## 2. Eight Core Mental Model Mappings

### Mapping 01: Finding Compatible Study Peers
* **User Expectation:** "I want to find students who are studying my exact course so we can work together."
* **Existing Mental Model:** Posting a generic message in a 300-person WhatsApp chat or Reddit thread; hoping someone replies; feeling awkward about cold-messaging strangers.
* **Proposed Interface Representation:** Searchable, filterable **Study Circle Directory** with explicit course/subject tags and compatibility match indicators.
* **Possible Terminology Confusion:** Confusing "Circles" with social media "Follower Circles" or algorithmic "Friend Suggestions".
* **Design Response:** Label clearly as **"Study Circles"**; display course codes, syllabus focus, and exact meeting days on every card.
* **Requirement ID:** `FR-005`, `FR-006`, `FR-007`.

---

### Mapping 02: Comparing Learning Compatibility
* **User Expectation:** "I want to know if this group studies like I do before I commit my time."
* **Existing Mental Model:** Guesswork; meeting someone once and finding out they want to chat while you want to work quietly; trial-and-error ghosting.
* **Proposed Interface Representation:** **Compatibility Percentage Badge & Explainable Breakdown Modal** detailing Subject (35%), Schedule (25%), Study Style (20%), Modality (12%), and Group Size (8%).
* **Possible Terminology Confusion:** Assuming the score is generated by opaque "AI magic" or judging personal student intelligence.
* **Design Response:** Provide an explicit "How this score is calculated" modal showing clear rule-based mathematical criteria with zero black-box claims (`DEC-003`).
* **Requirement ID:** `FR-009`, `FR-010`, `FR-011`.

---

### Mapping 03: Understanding Group Rules & Expectations
* **User Expectation:** "What are the rules of this group? Are we doing homework copying or actual learning?"
* **Existing Mental Model:** Ambiguous unstated expectations; awkwardness when someone doesn't prepare or dominates the conversation.
* **Proposed Interface Representation:** **Circle Charter & Ground Rules Card** on the circle profile, detailing primary study format, pacing goals, and preparation requirements.
* **Possible Terminology Confusion:** Confusing "Charter" with legal contracts or university administrative bylaws.
* **Design Response:** Use accessible, plain-language headings: **"How We Study"**, **"Expected Preparation"**, and **"Our Goals"**.
* **Requirement ID:** `FR-012`.

---

### Mapping 04: Joining or Requesting Membership
* **User Expectation:** "How do I get into this group without being socially rejected?"
* **Existing Mental Model:** Sending an awkward private DM asking "Can I join?" or clicking an uncurated public WhatsApp invite link that leads to a crowded channel.
* **Proposed Interface Representation:** Two clear, transparent pathways: **"Direct Join"** for open circles vs. **"Request to Join with Note"** for curated cohorts.
* **Possible Terminology Confusion:** Fearing that a "Request" is an official academic application or grading test.
* **Design Response:** Prompt for a friendly, casual 1-sentence note: *"Tell the host what you're working on this term"*; show immediate confirmation that the request was delivered.
* **Requirement ID:** `FR-013`, `FR-014`.

---

### Mapping 05: Tracking Commitments & Schedules
* **User Expectation:** "Where are all my study groups and when is our next meeting?"
* **Existing Mental Model:** Scrolling back through 500 WhatsApp messages to find a pinned date; cross-checking multiple calendar apps.
* **Proposed Interface Representation:** **Personal Study Dashboard** displaying chronological "Upcoming Study Sessions" with countdown badges and "My Circles" cards in a single unified view.
* **Possible Terminology Confusion:** Assuming the dashboard only displays university LMS course grades.
* **Design Response:** Prominently label as **"My Collaborative Learning Dashboard"** with clear action cards for upcoming sessions.
* **Requirement ID:** `FR-022`.

---

### Mapping 06: Creating a Study Circle (Host Role)
* **User Expectation:** "I want to start a small study group for my class, but I don't want 30 random people joining."
* **Existing Mental Model:** Creating a group chat link; posting it; panicking when it balloons to 40 people with zero accountability.
* **Proposed Interface Representation:** **Circle Creation Wizard** enforcing a hard capacity limit (2 to 8 members maximum) and a join policy toggle (Open vs. Approval Required).
* **Possible Terminology Confusion:** Confusing "Host" with a permanent administrative instructor or teacher role.
* **Design Response:** Frame the host as a **"Peer Facilitator / Organizer"**; emphasize that the host remains an active co-learner.
* **Requirement ID:** `FR-016`, `FR-017`.

---

### Mapping 07: Coordinating a Study Session
* **User Expectation:** "We need to set a time, place, and agenda for our next meeting."
* **Existing Mental Model:** Protracted 30-message back-and-forth debate; setting a Doodle poll; forgetting to agree on what to study.
* **Proposed Interface Representation:** **Session Scheduler Modal** capturing Date, Time, Duration, Venue / Meeting URL, and structured **Agenda Items**.
* **Possible Terminology Confusion:** Confusing an "Agenda" with a rigid corporate meeting schedule.
* **Design Response:** Provide helpful placeholder prompts: *"e.g., 16:00-16:45 Problem Set 3; 16:45-17:30 Joint Debugging"*.
* **Requirement ID:** `FR-020`.

---

### Mapping 08: Managing Attendance & RSVPs
* **User Expectation:** "I want to know if my peers are actually showing up before I travel to the library."
* **Existing Mental Model:** Members "liking" a message in WhatsApp but ghosting on the day of the meeting.
* **Proposed Interface Representation:** **One-Click RSVP Controls** (Attending / Tentative / Declined) with a real-time attendee list on the session card.
* **Possible Terminology Confusion:** Thinking an RSVP is a binding legal or academic commitment that carries penalties.
* **Design Response:** Allow graceful RSVP updates (e.g., "Change to Can't Make It") with a simple reason note so the host is informed respectfully.
* **Requirement ID:** `FR-021`.
